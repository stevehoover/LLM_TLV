User guidance for "Configure Using M5", verified by a manually reproduced
fully green run on this module in this exact mid-conversion state (m5 blocks
in place, registers still flat plain names like imm31, imm19_12_20).

The failure signature you are hitting (full FEV failing partitions named
serv_immdec.o_rs2_addr.4 / o_rs1_addr.4 / o_rd_addr.4 with basecase passing
and induction UNKNOWN) means MATCH LINES, not logic: gold (prepared.sv) still
has the generate scope names while your gate is flat, and without gold-match
lines EQY cannot cut the shift registers, so induction fails spuriously.

(4) SEMANTIC CHECK of the non-default arms, the other historical failure at
this step. The ORIGINAL Verilog in the separate branch and the W=4 branch
uses two sequential if blocks (`if (i_wb_en) begin ... end if (i_cnt_en)
begin ... end`), so when both enables are 1 the i_cnt_en assignment WINS,
and those shifts are NOT gated by i_immdec_en. If an earlier ternary
conversion gave those arms i_wb_en-first priority or immdec_en gating
(copying the shared arm's semantics), the non-default configs will fail FEV
with real counterexamples on the imm shift registers. The correct ternary
shape for those arms is:
   reg <= i_cnt_en ? <shift value> : i_wb_en ? <writeback value> : reg;
and in the W=4 arm additionally verify i22's shift source is i26 (a past
conversion had it self-holding behind an i_ctrl[3] mux, which is wrong).
Compare each arm against prepared.sv before trusting it.

  step when you rename nothing.
