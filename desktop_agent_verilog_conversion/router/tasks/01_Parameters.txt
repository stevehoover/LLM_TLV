If the module has any parameters or uses any tick-defines, additional FEV configurations can be established for alternate parameter sets. `fev.sh` will test each parameter set, each defined by a `fev_full_*.eqy` file.

Examine the use of module parameters and tick-define parameters in `prepared.sv` to determine a set of parameter sets to adequately test future refactoring steps. Make sure key generate scenarios are covered. Parameters should be chosen that impact elaboration and logic behavior. This includes generate `if` conditions, for example. Generate `for`s should be tested with no iterations, one iteration, and multiple iterations if possible. Avoid parameters that wouldn't be legal in the original code. It may be necessary to inspect project documentation or the broader code base to determine this. Avoid large parameter values to avoid large FEV runs. Keep the set (of sets) minimal, but sufficient.

Some tick-defines decide whether the module elaborates at all. For example, a module whose entire body is inside `` `ifdef RISCV_FORMAL `` elaborates to an empty module unless `RISCV_FORMAL` is defined, and FEV of two empty modules proves nothing. A define like this is a configuration to record, like any other. If the module elaborates to nothing, or to clearly less than the project uses, without some define, add `-Dname` (or `-Dname=value`) to both `read_verilog` lines of `fev.eqy` and of every `fev_full*.eqy`, and note the define and why it is needed in `tracker.md`.

If the module is part of a hierarchy that is being converted, its configurations must also reflect the modules above it. A submodule is only ever elaborated with the parameter values and tick-defines its ancestors give it. Look at every module that instantiates this one, directly or through intermediate modules. Where an ancestor has a conversion directory, use its `config.json` and `fev_full_*.eqy` files; otherwise use its source. For each configuration of each ancestor, work out the parameter values and tick-defines that this module ends up elaborated with, and include those as configurations here. Likewise, if this module contains submodules, the parameter values and tick-defines it passes down under each of its own configurations should be covered by configurations of the submodule conversions. Note in `tracker.md` any combination a submodule conversion does not yet cover, so it can be added there.

Collecting configurations from ancestors can grow the verification space quickly, since every ancestor configuration can imply a different configuration here. Keep it bounded. Drop combinations that elaborate to the same logic as one already in the list. Prefer values that change elaboration (generate conditions, loop counts, which `ifdef` branches are taken) over values that only change a constant or a width, and keep widths small as above. If the combined set still seems too large to run, list the full set in `tracker.md`, choose the subset you judge most important, and point out the gap to the user.

Create a corresponding `fev_full_*.eqy`, e.g. `fev_full_WIDTH_4_BYPASS_1.eqy`, for each parameter set. Initialize each as a copy of `fev_full.eqy`. For module parameters, uncomment the line `#chparam -set ...` and update it with one `-set <PARAMETER_NAME> <VALUE>` for each overridden parameter. For tick-defines, use `-Dname=value` on both `read_verilog` lines. Modify the match list if the parameters affect which signals will be elaborated.

Describe the parameter sets in `tracker.md`, including where each one came from (this module's own code or an ancestor's configuration).

If any modifications were made, run `fev.sh`. Since no changes were made to `wip.tlv`, failure points to an issue with `fev_full_*.eqy`. Compare thees versus `fev_full.eqy` to be sure you initialized them properly and also scrutinize the match lists. There could also be failures if you chose a configuration that is not supported in the original code.
